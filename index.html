Multi-Site Playwright Test Automation

A dynamic, zero-config test framework. Add any website to .env — the framework auto-discovers it, runs tests, and generates organized results with screenshots and retry cURLs.

🔍

Auto-Discovery

Add *_BASE_URL to .env and the framework finds it. Zero code changes needed.

🎯

Priority-Based

Tag tests with @priority:high|medium|low and run them in order with the priority runner.

📊

Rich Reports

JSON, HTML, and Excel reports. Per-site breakdown with screenshots, cURLs, and quality metrics.

⚙️

Multi-Site

Test unlimited websites simultaneously. Each gets its own project, auth, and result folders.

.env Config → Site Discovery → Project Generation → Test Execution → Organized Results

Installation

Prerequisites

  • Node.js ≥ 18 (recommended: v20+)
  • npm (comes with Node.js)
  • Google Chrome installed (Playwright uses the chrome channel)

Install the Framework

bash
git clone <your-repo-url>
cd hackthon-hackers
npm install

This installs Playwright, Express, ExcelJS, and all other dependencies defined in package.json.

Playwright ships its own Chromium browser, but this framework is configured to use your system Chrome via channel: 'chrome'. Make sure Chrome is installed.

Install the Report Viewer (Optional)

bash
cd report-viewer
npm install

Quick Start

Get up and running in 4 steps:

Install Dependencies

Run npm install inside the hackthon-hackers directory.

Configure Your Sites

Copy the environment template and add your website credentials.

Run Tests

Execute npm test to run all tests against all configured sites.

View Results

Check test-results/ for JSON reports, or start the Report Viewer dashboard.

bash
# 1. Install dependencies
npm install

# 2. Configure your .env
cp .env.example .env
# Edit .env with your real credentials

# 3. Run all tests
npm test

# 4. Run with priority orchestration
npm run test:priority

Environment Setup

The framework reads all configuration from a .env file. Start from the provided template:

bash
cp .env.example .env

Example .env File

env
# ─── Site 1: Blockpeer ────────────────────────
BLOCKPEER_BASE_URL=https://staging-react.blockpeer.finance
BLOCKPEER_EMAIL=your-email@example.com
BLOCKPEER_PASSWORD=your-password

# ─── Site 2: Crickbox ─────────────────────────
CRICKBOX_BASE_URL=https://crick-box07.vercel.app
CRICKBOX_EMAIL=your-email@example.com
CRICKBOX_PASSWORD=your-password

# ─── Optional: Adding a third site ────────────
# SPEAKSPORT_BASE_URL=https://staging.speaksport.ai
# SPEAKSPORT_EMAIL=your-email@example.com
# SPEAKSPORT_PASSWORD=your-password
# SPEAKSPORT_AUTH_ROUTE=/auth/login

# ─── Fallback credentials (used when site-specific ones are missing)
TEST_EMAIL=
TEST_PASSWORD=
Never commit your .env file. It contains real credentials. The .gitignore already excludes it.

Adding a New Site

Zero code changes required. Just add 3 lines to your .env:

env
MYNEWSITE_BASE_URL=https://staging.mynewsite.com
MYNEWSITE_EMAIL=qa@mynewsite.com
MYNEWSITE_PASSWORD=secret123

Optionally customize the login route (defaults to /auth/signin):

env
MYNEWSITE_AUTH_ROUTE=/login

What Happens Automatically

The framework will:

  • Discover the site from MYNEWSITE_BASE_URL
  • Create Playwright projects: mynewsite-setup, mynewsite-public
  • Run generic smoke tests against it
  • Use generic auth setup to log in
  • Generate results in test-results/<run>/mynewsite/
  • Create passed.json, failed.json, full_result.json
  • Organize screenshots in mynewsite/screenshots/

Test Structure

Tests are organized by site, priority, and auth requirement:

tests/ _generic/ # Runs against ALL discovered sites smoke.spec.ts # Page load, title, JS errors, a11y auth.setup.ts # Generic login for any site blockpeer/ # Site-specific tests auth.setup.ts # Custom auth (overrides generic) priority-high/ public/ auth-critical.spec.ts authenticated/ dashboard-critical.spec.ts priority-medium/ public/ auth-journeys.spec.ts authenticated/ business-modules.spec.ts priority-low/ public/ legal-and-edge.spec.ts crickbox/ # Another site auth.setup.ts crickbox.spec.ts authenticated/ app-authenticated.spec.ts
Tip: Tests in _generic/ run for every site. Tests in site-specific folders (like blockpeer/) only run for that site.

Generic Tests (Smoke Tests)

These tests run automatically against every discovered site. They validate basic health:

TypeScript
import { test, expect } from '@playwright/test';

test.describe('Smoke tests @api:core @priority:high', () => {
  test('home page loads with HTTP 200', async ({ page, baseURL }) => {
    const response = await page.goto(baseURL || '/');
    expect(response?.ok()).toBeTruthy();
  });

  test('page has a non-empty title', async ({ page, baseURL }) => {
    await page.goto(baseURL || '/');
    const title = await page.title();
    expect(title.length).toBeGreaterThan(0);
  });

  test('no uncaught JS errors on load', async ({ page, baseURL }) => {
    const errors: string[] = [];
    page.on('pageerror', (err) => errors.push(err.message));
    await page.goto(baseURL || '/');
    await page.waitForLoadState('domcontentloaded');
    expect(errors).toEqual([]);
  });
});

What the Smoke Tests Check

TestPriorityWhat It Validates
HTTP 200HIGHHome page returns a successful response
Non-empty titleHIGHPage has a <title> tag with content
Body rendersHIGH<body> element is visible (no crash)
No JS errorsHIGHNo uncaught JavaScript exceptions on load
Has linksMEDIUMAt least one <a> tag exists
Interactive elementsMEDIUMButtons, inputs, or selects are present
Lang attributeLOW<html lang="..."> is set (a11y)
Image alt textLOWAll <img> tags have alt attributes

Writing Custom Site Tests

To add tests specific to a site, create a folder matching its lowercase name under tests/:

Create the site folder

Create tests/mynewsite/ matching the prefix you used in .env.

Add an auth setup (optional)

Create tests/mynewsite/auth.setup.ts if the site needs custom login logic. Otherwise, the generic auth is used.

Organize by priority & auth

Place specs in priority-high/public/, priority-medium/authenticated/, etc.

Tag your tests

Use @api:<name> and @priority:<level> tags in test.describe.

Example Custom Test

TypeScript
import { test, expect } from '@playwright/test';

const BASE_URL = process.env.MYNEWSITE_BASE_URL!;

test.describe('Landing Page @api:landing @priority:high', () => {
  test('hero section is visible', async ({ page }) => {
    await page.goto(`${BASE_URL}/`);
    await expect(page.locator('h1')).toBeVisible();
  });

  test('CTA button works', async ({ page }) => {
    await page.goto(`${BASE_URL}/`);
    await page.click('[data-testid="cta-button"]');
    await expect(page).toHaveURL(/signup/);
  });
});
Once you create tests/mynewsite/, the config auto-detects it and uses your custom auth & test files.

Tags & Priorities

The framework uses inline tags in test.describe() titles to organize and filter tests:

API Tags

Format: @api:<name> — groups tests by feature area.

TypeScript
test.describe('Login Flow @api:auth @priority:high', () => {
  // Tests here are grouped under "auth" API
});

test.describe('User Dashboard @api:dashboard @priority:medium', () => {
  // Tests here are grouped under "dashboard" API
});

Priority Levels

TagLevelWhen to Use
@priority:highHIGHCritical paths — login, core features, payment flows
@priority:mediumMEDIUMImportant features — forms, navigation, user journeys
@priority:lowLOWEdge cases — legal pages, accessibility, error states

The priority runner uses these tags to execute tests in order: high → medium → low.

How Site Discovery Works

The core magic of this framework. No config files to edit — just environment variables.

Scan Environment

utils/siteDiscovery.ts scans all process.env variables on startup.

Match Pattern

Any variable ending in _BASE_URL is treated as a site definition.

Extract Name

The prefix becomes the site name (e.g., BLOCKPEER_BASE_URL → blockpeer).

Check for Custom Tests

Checks if tests/<sitename>/ exists for custom tests and auth.setup.ts for custom auth.

Generate Projects

playwright.config.ts generates 2–3 Playwright projects per site: setup, public, and optionally authenticated.

Execute & Report

The reporter organizes all output by website name with per-site JSON aggregation.

TypeScript — utils/siteDiscovery.ts
export function discoverSites(
  env: Record<string, string | undefined> = process.env
): SiteConfig[] {
  const sites: SiteConfig[] = [];

  for (const key of Object.keys(env)) {
    if (!key.endsWith('_BASE_URL')) continue;

    const prefix = key.slice(0, -'_BASE_URL'.length);
    const name = prefix.toLowerCase();

    sites.push({
      name,
      baseURL: env[key],
      email:    env[`${prefix}_EMAIL`]    || env.TEST_EMAIL,
      password: env[`${prefix}_PASSWORD`] || env.TEST_PASSWORD,
      authRoute: env[`${prefix}_AUTH_ROUTE`] || '/auth/signin',
      hasCustomTests: fs.existsSync(`tests/${name}`),
      hasCustomAuth:  fs.existsSync(`tests/${name}/auth.setup.ts`),
    });
  }

  return sites;
}

CI / CD Integration

The framework includes a GitHub Actions workflow that runs on push/PR to main:

YAML — .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-15, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
    - uses: actions/checkout@v4
    - name: Use Node.js 20
      uses: actions/setup-node@v4
      with:
        node-version: '20'
        cache: 'npm'
    - name: Install dependencies
      run: npm ci
    - name: Run tests
      run: npm run test
    - name: Upload test results
      if: always()
      uses: actions/upload-artifact@v4
      with:
        name: test-results-${{ matrix.os }}
        path: test-results/
        retention-days: 30

CI Features

  • Multi-OS matrix — tests on Ubuntu, macOS, and Windows
  • Coverage verification — checks that all coverage-tagged tests pass
  • Artifact upload — test results are saved as build artifacts for 30 days
  • Fail-fast disabled — all OS jobs run even if one fails
Tip: Set your site credentials as GitHub Secrets and reference them in the workflow to run real E2E tests in CI.

Architecture

How all the pieces fit together:

hackthon-hackers/ .env # Site credentials (git-ignored) .env.example # Template playwright.config.ts # Dynamic config (generates projects from .env) global.setup.ts # Validates env vars on startup utils/ siteDiscovery.ts # Scans *_BASE_URL env vars testResultManager.ts # Folder creation + JSON writing reporters/ priorityResultReporter.ts # Custom reporter: 3 JSONs + screenshots scripts/ run-priority-tests.mjs # Orchestrator: runs by site + priority export-test-report.mjs # Generates Excel report clean-test-results.mjs # Wipes test-results/ server/ index.ts # Express report API (port 4000) reportService.ts # Data layer for report API tests/ _generic/ # Runs against ALL sites blockpeer/ # Site-specific tests crickbox/ # Another site report-viewer/ # Next.js dashboard (separate project) app/ # Pages + API routes components/ # UI components lib/ # Report reader + types

Key Design Decisions

  • Convention over configuration — Env var naming drives everything. No YAML, no JSON config files for sites.
  • Generic + specific — Smoke tests run everywhere; custom tests extend specific sites.
  • Custom reporter — The PriorityResultReporter produces organized per-site JSON during test execution.
  • Decoupled viewer — The report dashboard is a standalone Next.js app that can read filesystem or API.
